# Torch 移植性能根因诊断（2026-09-28）

当前证据支持的是：**此前 Torch 实现存在可定位的计算路径问题，不能用其速度代表 Torch 上限。** 之前在分析具体瓶颈之前投入开发组比较、并据此讨论框架路线，顺序不合理。本次停止 compute_lab_v5 批次并保留完成结果，仅进行下列固定输入控制实验。

## 边界与测量

- 同一台 RTX 4090；Torch 2.8.0+cu128，cuDNN 9.10.2；官方 EMA 权重。
- 固定 debug 病例 `0X1531B80C56297FD2.hdf5`，缓存组 `2`，相同观测、历史、掩膜与显式噪声。
- FP32，TF32 关闭，2 粒子，窗口 3，50 次热启动更新，每步 DPS，14 条预算；不减少计算步数，不重新训练。
- 每项预热 3 次、同步计时 20 次；编译/加载不计入这些核心计时。单独运行 profiler，不用插桩速度计算 FPS。
- 这是固定帧根因诊断，不是完整视频、闭环确认集或可采用性结论。约 78 ms 的旧官方微基准是背景数据，不直接作为本次固定输入的公平参照。

## 1. 确定性控制揭示的上采样反向路径

|受控配置|同步 Graph 核心均值|同输入重复与 Graph/未捕获核对|
|---|---:|---|
|原插值，确定性开启|202.65 ms|四项输出最大差均为 0|
|原插值，确定性关闭|100.96 ms|后验样本重复最大差 0.2856，选线也变化|

不能把关闭确定性直接当作合格加速方案。这个开关对照只证明其计算路径有显著时间代价；不能把全部时间差直接归给某一个内核。

进一步核对安装版本 PyTorch 的 `_upsample_linear` 源码，以及 profiler 的输入尺寸：三处 2 倍双线性上采样，分别在 14→28、28→56、56→112 尺寸上，通过四邻点索引读取分解。梯度需要累加回输入，确定性路径每步出现 12 次索引累加。

50 步 Graph 的独立 kernel trace 中：

- `indexing_backward_kernel_stride_1`：600 次，约 68.95 ms。
- 名字含 RadixSort 的排序内核：2,200 次，合计约 9.25 ms。
- 还有配套拷贝、填充和检查等工作。CPU 算子事件和 GPU kernel 事件分别记录，汇总只统计 kernel，避免重复计数。

**定向干预：**诊断进程将这三处上采样改写为分离的一维半像素插值，使用相邻切片与拼接，保持数学插值定义和输入梯度；不写自定义 CUDA 内核。原始正式入口不改。

结果：仍开启确定性，Graph 从 **202.65 ms 降至 97.21 ms**。上述索引累加与排序内核在 trace 中消失；Graph 与未捕获路径、同输入重复均一致。这比仅观察“Graph 比 compile 快”更直接地定位了瓶颈。

**数值限制：**三个 CPU float64 算子测试覆盖边界、退化 1×1 尺寸和随机上游梯度，前向及输入梯度均通过 2e-14 容差。但浮点累加顺序改变后，50 步后验样本相对原 Torch 的最大差为 0.2196、平均绝对差约 0.000417；投影图最大差 0.1359；该单帧选线相同。它没有通过既定 2e-4 状态门槛，不能自动成为工程替代，也不能从单帧认定质量下降或质量等价。

## 2. 布局转换是另一处可干预开销

原 Torch 移植使用 channels_last，并允许 Inductor 布局优化，但被选中的卷积路径仍反复转换布局。原版本以及分离插值版本每帧均出现约 **9,500 次 NHWC/NCHW 转换，约 19 ms**。

第二个定向干预只改变布局策略：权重和输入统一连续 NCHW，同时关闭 Inductor 自动布局优化；仍使用分离插值、确定性算法、FP32 和相同 50 步。

Graph 从 **97.21 ms 降至 75.10 ms**，trace 中这两类布局转换内核的调用数降为 0，本次同输入重复及 Graph/未捕获结果仍一致。布局策略也会影响卷积算法选择，不能把全部 22.11 ms 收益机械等同于删除转换内核的时间。

这两个改写属于工程修改的意图，但数值结果另行判定。当前仅是诊断性原型，没有接入正式候选调度、没有修改 baseline。

## 3. 主机开销与 Graph 的实际作用

原确定性实现每帧 compile 调用约 556–561 ms，Graph 约 203 ms；Graph 消除了很大一部分调度开销，但保留了低效的 GPU 内部路径。因此此前说“Graph 相对 compile 有收益”虽在数字上成立，却没有回答它为什么比 JAX 慢，也不能据此宣布移植成功。

两次定向干预使当前固定帧从约 203 ms 到 75 ms，证明存在实现优化空间。它还不能证明原算法在完整闭环中达到 32 FPS，也不能证明跨框架数值等价。

### 完全相同输入的 JAX 参照

最后在独立 JAX 进程中，用相同观测、历史和显式噪声重放官方采样公式，同样预热 3 次、同步计时 20 次。没有与 Torch GPU 工作负载并行运行。

|固定输入实现|均值|p95|核心吞吐 1/均值|
|---|---:|---:|---:|
|JAX 显式噪声重放|78.45 ms|78.61 ms|12.75 FPS|
|原 Torch Graph，确定性开启|202.65 ms|202.77 ms|4.93 FPS|
|分离插值 Torch Graph|97.21 ms|97.32 ms|10.29 FPS|
|分离插值＋连续 NCHW Torch Graph|75.10 ms|75.28 ms|13.31 FPS|

最后一个诊断原型相对 JAX 此固定输入的时间约少 4.3%，但这只是单次会话、一个固定帧的微基准，不足以宣布普遍超越 JAX，更不是完整任务 FPS。数学设置相同也不保证浮点状态相同。

三个 Torch 版本均未通过与 JAX 的 2e-4 状态核对，且其选线掩膜相对 JAX 均有 2 / 112 个位置不同。原 Torch 后验样本最大差 0.3741、平均差 0.00110；最后一个诊断原型最大差 0.3916、平均差 0.00126。最大差不能替代病例质量评价，当前不能断言最后一个版本质量相同或质量更差。

这次确认的是**慢在哪里，以及针对这些路径确实能提速**；尚未完成的是让提速实现达到可接受的闭环质量或严格等价性。正式 baseline 保持不变。

## 4. 四个近似版本的失败应如何解释

`short_torch_25_fp16/50_fp16/25_bf16/50_bf16` 均在 `validate_compiled_gradient` 中被拦下，尚未完成病例质量评估。

- FP16 的 compiled/eager 单步输出最大差约 0.000569，143 / 75264 个元素不满足 2e-4 绝对/相对容差。
- BF16 最大差约 0.004710，44079 / 75264 个元素不满足容差。

这些记录说明当前编译路径没有通过既定内部核对，**不等于硬件不支持该精度，也不等于病例质量不合格**。本轮未放松门槛、未将其静默当作合格版本继续运行。若后续研究它们，需要分别记录编译数值差异与独立质量验证，不得混称无损。

## 对学长说法的回应

“移植并优化算子和计算图有可能加速”不能被此前的低效实现否定，本次诊断也找到了实际优化空间。他同时说其尝试有明显精度下降，这与必须独立核对质量的原则一致。

“4090 上 32 FPS”目前仍缺少对应代码、精度、热启动步数、DPS 频次、粒子数、同步计时边界和质量结果。既不能据当前实现说它不可信，也不能把它直接当作保持官方配置和质量的已证实目标。这里不推测其个人实现。
