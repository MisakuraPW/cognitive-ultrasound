# 12 个转换失败病例诊断（2026-09-10）

本轮仅做只读诊断，不停止正在运行的转换，不改原始 AVI、HDF5、官方划分或运行中的转换算法。用户要求先让本轮结束，再集中处理。

## 实测结论

- 12 个 AVI 均通过 imageio/FFmpeg 和 OpenCV 两条读取路径的全视频解码，帧数均与 FileList.csv 一致，imageio 输出均为 112×112×3。未发现截断或解码异常。这不等于已经与原始发布方文件哈希一致；本地 SHA256 仅用于记录与后续复核。
- 异常发生在上游 `H5Processor.get_split()`：先对经过分割的首帧调用 `accept_shape()`，再断言接受结果与固定清单是否纳入该病例一致。异常早于极坐标插值，与缓存插值几何无关。
- 当前实现用 imageio 读取 RGB，再用 PIL `convert("L")` 转灰度。10 个 train 病例中，9 个未达到右侧分数 5，另 1 个 `0X4889B480C7F3DE83` 的左侧分数为 0.090196，低于 0.1。
- 上游历史提交 `71e4e42f5f0d0330d91d1afee76c736c2e9e7beb`（2025-08-25）将 OpenCV 读取改成 imageio/PIL。其父版本 `cc04c744d3f264efa26b453521ac0eb0cea2419a` 使用 `VideoCapture` 读取 BGR，然后调用 `COLOR_RGB2GRAY`，即红蓝权重与当前处理相反。2025-11-17 的 `99860751cce87491ef300a47899a76dda1d4dc90` 又将读取入口从 `load_video` 改为 `load_avi`，保留 PIL 灰度方式。
- 实际重放旧版 OpenCV 灰度操作后，10 个 train 病例全部接受，`0X6E4159BB40A86E64` 则正确拒绝。这是 11 个病例存在历史灰度兼容问题的直接证据；尚不能单凭此证明发布数据使用了哪个精确版本。
- RGB 三通道均值也是早期诊断对照，但没有证据表明它是官方算法，不能据此改用均值。

## 本轮结束后的处理方案（尚未应用）

优先保留当前已生成文件及统一的 PIL 灰度、分割、cubic 插值和像素范围。将**固定官方划分作为病例归属依据**，只对经过上述解码检查、原始文件 SHA256 固定的病例应用显式兼容清单：10 个 train 仍进 train，2 个 rejected 仍留 rejected。对这些病例保留自动筛选分数和冲突记录，不再让重复筛选覆盖已提供的固定清单。新的未知冲突继续报错，不能关闭所有断言或放宽所有病例阈值。

实现时应在项目适配层加入可审计的例外机制，不改 vendor 固定源码；记录原始 SHA256、理由、官方划分清单哈希、当前灰度实现和兼容版本。只补做没有发布的文件，结束后重新做完整审计。需要测试例外只对指定哈希与划分生效、未知病例仍失败、输出像素仍与当前上游 PIL 路径一致、已有文件不改写。

该方案解决的是当前固定代码与固定病例清单之间的不兼容，不代表恢复了历史发布数据的逐像素内容。不能只给这 12 个病例改用历史 OpenCV 灰度，那会混用两套像素处理。如果后续对官方发布 HDF5 的对照证明必须严格恢复历史像素流程，应另行评估全体数据受影响的范围和统一迁移方式；不得未经验证声称现有所有图像与论文训练输入逐像素一致。

诊断程序：`scripts/diagnose_conversion_failures.py`。本次逐病例哈希、阈值、全帧接受统计及双路径帧数保存在 `results/local_conversion/failure_diagnosis.json`（忽略提交的本地实验记录）。只使用本机已有依赖，不创建另一套 ML 运行环境。

历史证据可在本地固定 zea 仓库执行 `git show 71e4e42f -- zea/io_lib.py` 与 `git show cc04c744:zea/io_lib.py` 复查；对应 [上游灰度读取变更](https://github.com/tue-bmd/zea/commit/71e4e42f5f0d0330d91d1afee76c736c2e9e7beb)。
