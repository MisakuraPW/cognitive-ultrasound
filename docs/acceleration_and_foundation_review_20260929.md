# 加速效果重新评估与实验基座交接报告

日期：2026-09-29。依据：已下载并校验的 compute_lab_v5 原始结果、Torch 根因诊断和四项补跑证据。本报告只重新整理与计算已有统计，不新增实验，不改变默认 baseline。旧报告、失败日志和旧结论均保留。

**当前结论：已经找到效果保持不变的工程改动，也找到质量损失受控、收益更大的近似加速。两者必须分开使用。推理暂时没有充分理由整体迁移 Torch；训练方面，BF 三个模块的 TensorFlow 图模式已有实测收益。实验基座已具备开始具体研究所需的运行、比较、恢复和记录能力，但不代表后续任何新模型都已验证。**

## 1. 按“是否影响最终效果”重新分类

这里的“效果”需要同时看两件事：一是生成图像、选线和历史状态有没有改变；二是改变后，重建质量有没有变差。质量相近并不代表算法行为不变。

|使用分类|本轮对应项|实际证据|应如何使用|
|---|---|---|---|
|**已验证不改变结果**|JAX 常量缓存；开发组中的预取、减少传输、异步写入及其组合|对应已测轨迹逐位一致，离散选线和预算一致|可在验证范围内作为工程替代；是否值得启用还要看完整任务是否更快|
|**会改变结果，但已测质量损失受控**|JAX 50步 FP16、25步 FP32、25步 BF16|7线确认通过质量门槛；状态和选线不等价|作为独立近似版本；采用后，在相同版本上比较新方法与 baseline|
|**已测质量不达标**|JAX 50步 BF16、50步中仅10次/5次 DPS|14线开发筛选失败|本轮不推荐，不因速度快而忽略质量|
|**结果会变化，证据不足以判断最终质量**|Torch 工程移植/算子优化原型；四个 Torch 低精度补跑短测|部分只有固定输入诊断或两例短测；未通过严格等价|保留为研究实现，不当成无损替代，不加入默认运行路径|
|**训练短测容差内一致**|BF codec/prior/filter 的 graph 对 eager|200步通过容差比较，各自精确续训通过|可推荐用于这些已测训练负载；不能承诺完整收敛不变|
|**训练轨迹已出现超容差差异**|CASL graph 对 eager|200步参数/梯度等综合检查和损失比较未通过|保持 eager 训练参照；不能只按耗时采用 graph|

这与原来的 A/B 修改类型并不矛盾。A 表示“意图保持算法和精度设置”，不能直接翻译成“无损”；B 表示“主动改变精度或计算步骤”，也不能直接翻译成“效果一定更差”。

## 2. 这次比较的条件和证据范围

主参照为官方权重、JAX 推理、FP32、TF32 关闭、2 粒子、窗口3、冷启动500步、热启动50步、逐步 DPS。减步版只把热启动改为25步；所有近似版冷启动仍是500步，但 FP16/BF16 版本的冷启动也使用相应精度，并非冷启动统一 FP32。

服务器记录为 RTX 4090 24GB，CPU 配额16，内存限制120GiB；JAX 0.6.2、TensorFlow 2.20.0，Torch 2.8.0+cu128 使用独立 Python 环境。以下性能是这个实际软件栈与工作负载的记录，不是框架理论上限。

- 排除已用于历史开发和确认的 validation 病例后，锁定2个调试、8个开发、32个确认病例；本轮不使用 test。
- 开发：14线、2种子，每例前128帧或全部可用帧，共2,040条帧—种子记录/版本。
- 确认：按用户最终要求，只做7线、3种子、32例完整视频，共17,367条帧—种子记录/版本。14/28线确认取消。
- 帧先在种子内汇总，种子再在病例内汇总，最后病例等权；置信界按病例配对 bootstrap。17,367帧不视为17,367个独立病例。
- 固定输入诊断使用相同观测、历史和显式噪声；实际闭环允许各版本使用自己的历史和选线，同时控制噪声来源。它们回答不同问题。

质量门槛：病例平均 PSNR 下降≤0.1dB、SSIM下降≤0.002、MAE相对增加≤1%；确认集单侧95%上界也要满足同一门槛。最差病例保护为≤0.5dB、≤0.01、≤5%。PSNR/SSIM沿用当前极坐标 uint8 口径，另报归一化浮点 MAE；不把它们称作 RF 真值质量或临床诊断效果。

**7线结果足以指导这一阶段工具选择。它不是其他预算的实测结论；也不再要求为此追加14/28线准备实验。**

## 3. 不改变结果的加速：有收益，但主要在外围开销

### 3.1 开发组的工程候选

以下各项在14线开发轨迹中均逐位一致，图像、选线和预算未变化。

|版本|具体改动|热帧闭环 ms|完整任务 s|相对参照完整任务提速|
|---|---|---:|---:|---:|
|official|参照|85.48|314.32|1.000×|
|jax_prefetch|有界线程预取，按原顺序消费帧|86.39|309.89|1.014×|
|jax_constants|缓存固定形状/常数的诊断熵核，减少重复工作|82.18|315.00|0.998×|
|jax_transfers|减少重复主机/设备传输|85.83|323.90|0.970×|
|jax_async_output|单写入线程，有界队列与输出缓冲复制|86.31|292.29|1.075×|
|jax_combined|上述四项组合|83.99|265.17|1.185×|

这里最好的**完整任务**收益出现在组合版，约减少15.6%耗时；但它只有开发组证据。按事先规定的“热闭环时间”选择规则，常量缓存进入确认。这个结果也说明，未来选择执行配置时应先决定目标是交互式帧延迟，还是整批实验完成时间；二者的最优项可能不同。

预取不等于越多线程越快，减少传输也不保证总耗时下降。当前采样核心原本已有 JIT 和粒子 vmap，本轮没有把这些已有能力当作新增贡献。

### 3.2 常量缓存的7线确认

常量缓存与官方的17,367条记录在已比较的状态、图像、动作上逐位一致，质量变化为零。热闭环从85.20ms变为82.34ms，约1.035×，但完整任务从38.98分钟变为40.26分钟，反而多约3.3%。采样核心两者都约79.22ms，基本没有变化。

**评价：它是验证通过的结果保持型工程改动，但本轮没有证明它缩短整批运行时间。** 不能把“闭环快3.5%”写成“实验整体快3.5%”。完整任务包含初始化、读取、配对诊断和结果写入；本轮也没有多次整批重复来分离系统波动，不能强行解释这1.28分钟差异的单一原因。

## 4. 会改变结果的加速：质量、速度与代价

### 4.1 7线确认的主要结果

热帧统计排除每条序列的第0帧冷启动和第1帧首次热签名；核心计时同步等待 GPU，闭环还包括传输和状态导出。完整任务包含读取、输出与初始化，不能用热帧时间直接换算整轮成本。

|版本|热核心 ms|热闭环 ms|热闭环提速|完整任务 min|完整任务提速|
|---|---:|---:|---:|---:|---:|
|official FP32/50|79.22|85.20|1.000×|38.98|1.000×|
|常量缓存 FP32/50|79.21|82.34|1.035×|40.26|0.968×|
|FP16/50|63.40|69.66|1.223×|36.38|1.071×|

### 4.2 为什么质量通过后仍必须作为独立版本

在所有17,367条确认记录中，“下一次选线集合与官方不完全相同”的记录数为：FP16/50有17,362条，FP32/25有17,238条，BF16/25有17,366条。这个统计只表示某帧的整组选线至少一处不同，**不是这些帧里每一条扫描线都不同**，也不是额外耗费了预算；所有确认记录实际线数均为7。

这说明，即使 FP16/50 的平均画质极接近，闭环行为也已改变。后续研究动态预算、预测式选线时，这种变化尤其相关：应让新方法和对照方法使用相同的精度、迭代数和 DPS 规则，不能把一方的加速修改混进创新收益。

附加描述性指标也保留如下；它们未另设确认通过门槛，不替代前述质量判定。

|版本|时序误差，越低越好|双方共同未观测区域 MAE：候选 / 官方|
|---|---:|---:|
|official|0.079144|0.084485 / 0.084485|
|FP16/50|0.079059|0.084121 / 0.084241|
|FP32/25|0.075034|0.082680 / 0.084239|
|BF16/25|0.075190|0.083246 / 0.084248|

时序误差比较“重建相邻帧变化”和“真值相邻帧变化”，不是简单鼓励视频变平滑。共同未观测区域由每个候选与官方共同确定，因此不同候选的官方分母区域也不同，宜在每行内配对解释。

### 4.3 没有通过筛选的近似方案

|14线开发候选|热闭环 ms|病例平均损失：PSNR下降 / SSIM下降 / MAE增加|判断|
|---|---:|---|---|
|BF16/50|69.08|0.06880dB / 0.002548 / 1.016%|SSIM、MAE超过门槛|
|FP32/50，仅10次 DPS|56.79|−0.35997dB / 0.013568 / −0.578%|PSNR改善但SSIM明显退化，不通过|
|FP32/50，仅5次 DPS|52.99|0.52217dB / 0.060376 / 11.918%|明显不通过|

FP16/25通过开发筛选，热闭环38.61ms；同类 BF16/25为38.46ms，依预定速度规则选择后者确认。未进入确认不等于不支持。50步 BF16未通过而25步 BF16通过，也不能归纳成“BF16永远更好/更差”；步数与精度组合需要分别记录。

**本轮建议：**若用户愿意使用近似版本，FP32/25是改动较单纯且收益明显的选择；BF16/25是已确认候选里更快的选择。FP16/50保留迭代数，但整批收益较小。以上是供选择的结论，当前配置仍保留 official，没有自动切换。

采用这些冻结权重推理版本需要重新建立同配置的评价 baseline，**不需要为了换推理精度/步数重新训练完整 CASL**。若以后修改训练精度、损失或训练过程，则是另一项训练实验。

## 5. Torch 路线究竟查清了什么

在14线开发中，原 Torch eager 热闭环约1740.56ms，原 Torch Graph约205.56ms，官方JAX约85.48ms。Graph 相对 eager 有收益，但仍不足以替代JAX；这个实现的速度不能代表Torch上限。

进一步做了固定输入、同权重、FP32、50步、逐步DPS、2粒子的受控诊断，预热3次、同步计时20次；profiler单独执行。

|固定输入诊断路径|同步核心 ms|解释|
|---|---:|---|
|原 Torch Graph，确定性开启|202.65|初始实现存在大量上采样反向索引累加及布局转换|
|原路径关闭确定性|100.96|重复输出和选线会变，不能当作无损提速|
|改为分离的一维半像素插值，确定性开启|97.21|索引累加及相关排序内核消失|
|再统一连续 NCHW、关闭自动布局优化|75.10|约9,500次布局转换降为0|
|同输入 JAX 显式噪声重放|78.45|本次诊断的公平参照|

原确定性路径的每帧50步中，定位到600次索引反向累加、约68.95ms；布局转换约19ms。定向改写确认存在真实的实现瓶颈，而非只靠总FPS猜测。

但是，最后原型虽然固定帧比JAX少约4.3%时间，仍未通过跨框架2e-4状态核对，选线掩膜有2/112个位置不同；没有完整确认质量。**目前查清了主要性能瓶颈与可行干预，没有得到可替代JAX的无损Torch版本。**

四个Torch低精度补跑也已完成，分别为50步FP16/BF16、25步FP16/BF16。热闭环约158.61、157.96、80.26、81.35ms。这些仍是原候选实现的2例×4帧短测，并未叠加上述诊断原型，不能把两个实验的收益拼起来。四项都不满足compiled/eager的严格容差，有限性、重复稳定性及图捕获检查通过；50步FP16的调试SSIM门槛未过，其余三项调试质量过线，均不足以替代确认。

最后修复的是“有限数值差异被误当程序崩溃”的流水线分类，保留不等价证据后继续B类质量诊断；没有靠放宽2e-4阈值把失败改成无损通过。保留中间精度舍入的第一种修复尝试也未奏效，失败记录保留。

对学长说法的评价：**移植、算子及图优化存在提速空间，有实测支持；在什么配置和质量条件下达到32FPS，本项目没有验证。** 学长自己提到精度下降，因此其结果也不能直接归入“不影响效果”。当前继续沿用JAX推理更有依据，这不否认Torch后续优化空间，也不把Torch适配变成开展毕设的前置任务。

## 6. 实验基座具体搭了什么

基座的用途是让以后每个研究问题都能知道“用了什么数据和配置、实际跑了什么、是否公平、断了怎么恢复、结果在哪”。它不代替研究问题、预测和创新设计。

### 6.1 环境检查与运行身份

实现了JAX、TensorFlow、Torch分环境、分进程检查，记录Python、库版本、GPU/驱动、CPU配额、内存限制，并实际运行GPU卷积及输入梯度，避免“能import就算能训练”的判断。环境、代码、权重、配置、数据形成身份记录；变更后不能直接把不同配置的结果混入原目录。

本轮三框架GPU检查已通过。保留一个报告限制：`available_ram`来自宿主可见的psutil空闲量，容器下可能超过其配额；本次确实如此。应以120GiB容器限制和实际占用约束容量，不能把宿主可见空闲值当可用额度。现有工具不是已经在所有云容器/显卡上验证过的万能资源调度器。

实现位置：`compute_lab/environment.py`、`hardware.py`、`compute_lab/readiness.py`。证据：`probe/probe.json`、`identity.json`。

### 6.2 数据读取、缓存、预取和输出

保留已转换的极坐标HDF5作为输入，检查形状、有限性、值域及归一化；固定病例、顺序和帧索引。预取使用有界队列，异步写入复制缓冲区，防止上一帧被下一次图执行覆盖。按“帧索引＋内容”哈希核对候选，不以速度掩盖漏帧、乱序或输入变化。

真实238帧读取测试：串行1.613/1.603秒，预取深度1为1.655/1.649秒，深度2为3.743/3.707秒，深度4为3.305/3.217秒，整段缓存为0.145/0.118秒，内容与顺序全部通过。

这说明一次读入当前片段很有价值，但**不是整个实验快十多倍**；数据读取只占总任务一部分。测试未强制清空操作系统页缓存，不能把第一次应用读取称为真正冷盘读取。也没有据此自动把全量数据装入内存。

实现位置：`compute_lab/data.py`。证据：`throughput.json`、相应开发组轨迹。

### 6.3 可比较的实验协议与诊断

建立独立的 debug/development/confirmation 名单、权重和文件哈希、种子与预算记录。实现共同输入重放、算子/输入梯度核对、状态和选线核对，再进行真实闭环。质量判定、数值等价和运行成功分别存储。

速度分加载/编译、冷启动、同步核心、含传输闭环和完整任务；同时记录p50/p95、进程RAM、框架可获取的显存统计。框架显存数字并非统一的整卡峰值，不能脱离分配器口径比较。独立profile用于找瓶颈，不混进正式计时。

实现位置：`compute_lab/protocol.py`、`diagnostics.py`、`inference.py`、`engines.py`、`report.py`。证据：`manifest.json`、`versions.json`、`matrix.json`、`selection.json`、质量—速度图。

### 6.4 短测、容量建议与跨设备校准

候选先短测估时，固定清单和成本筛选，失败保存原因，不因结果不好无限加配置。批量容量测试在独立子进程中做真实优化器更新；本轮CASL batch1/8/16/32/64/128都能执行，batch32框架峰值约4.92GiB，batch128约19.12GiB。

这只是单步容量探针；batch>32时有重复输入，不代表大batch吞吐最佳、正式训练安全余量充足或收敛更好。正式科学batch保持32，学习率、训练步数、粒子数和序列长度均不因“显存没满”自动修改。换卡后重新探测和短测，但现有工具只会在有限候选中推荐，不保证搜索全局最佳参数。

实现位置：`compute_lab/suite.py`、`scheduling.py`。证据：`estimates.json`、`scheduling.json`、`capacity.json`。

### 6.5 四种真实训练负载与恢复验收

短训覆盖CASL扩散模型和学长论文启发实现中的BF三个模块：codec负责图像与潜变量表达，prior负责潜在状态预测，filter负责结合观测更新状态。BF实现是论文驱动的项目原型，不是取得了学长原代码。

每个负载保存相同初始模型/优化器快照和200步固定真实HDF5批次；CASL batch32，BF按当前片段负载执行。所有短训是FP32。BF分阶段设置可训练模块，逐步核对冻结部分不变；CASL还跟踪EMA。每步检查损失、梯度、参数与优化器有限性，校准状态与正式训练输出隔离。

**这里的训练 graph 是 TensorFlow `tf.function`（本入口 `jit_compile=False`），不是前面Torch推理的CUDA Graph。**

|训练负载|eager 200步进程总耗时 s|graph 200步进程总耗时 s|本次倍率|graph/eager比较|当前工具建议|
|---|---:|---:|---:|---|---|
|CASL|202.35|118.22|1.71×|不等价|eager|
|BF codec|41.28|19.12|2.16×|容差内一致，非逐位|graph|
|BF prior|44.28|18.62|2.38×|容差内一致，非逐位|graph|
|BF filter|272.77|44.79|6.09×|容差内一致，非逐位|graph|

表中包含进程初始化、读取、同步及检查，不能当成纯更新内核倍率，更不能直接承诺完整训练按同倍率提速。CASL损失轨迹最大差约0.002308且综合状态比较未过；不能用graph更快这一点抹去差异。

每种模式另做“100步后进程退出，再在新进程恢复到200步”，与其自身连续200步对照。**四种负载×两种模式共8组，最终参数、优化器、适用的EMA、最终梯度和恢复段损失均逐位一致。** 恢复包括全局步数和固定数据序列位置；噪声由全局步数显式生成，避免隐藏RNG推进差异。

这是已实现的固定批次短训工作器的恢复保证。旧完整CASL训练入口仍有其epoch边界恢复限制，新方法若加入数据增强、随机采样、额外状态或不同优化器，需要把这些状态纳入检查，不能只加载权重就声称精确续训。200步验证也不证明完整模型收敛和最终指标等价。

实现位置：`compute_lab/training.py`、`belief_filter/`。证据：`training_report.json`、`training/*.batches.json`、初始快照及`jobs/train_*`。

### 6.6 运行、停止、恢复和异常收尾

统一入口支持 `probe → calibrate → run → report`，另有`status / stop / resume`。协调器锁防止同一目录重复启动；PID与创建时间共同识别所属进程，停止时回收工作器子进程；OOM/异常退出留证据，恢复时复用身份一致的完成任务。序列中断通常按未完成病例重新计算，不承诺任意帧零损失恢复。

本轮实际排查过重复启动锁、环境/依赖与身份兼容、编译内部数值检查、图捕获变化输入及输出缓冲、HDF5文件描述符继承等问题。修复结果与原结果分目录，不能修改旧收据来假装原来已经通过。

OOM子进程回收有本地受控功能测试；本轮batch容量扫描没有逼出真实GPU OOM，不能把它说成所有真实OOM情形都已验证。换卡身份失效有协议保护，但本轮并没有跨多种GPU重复整套质量确认。

实现位置：`compute_lab/suite.py`、`migration.py`、`scripts/run_compute_lab.sh`。这一轮已结束，不应再次运行旧全量`start`来查看报告。

## 7. 现在可以怎样开始自己的实验

**准备工作可以在这里结束。** 已有基础能够支持从明确研究问题开始，使用小规模MVP、固定对照、记录预测，再按结果决定是否扩大；不需要先完整重训CASL或做完整论文复现。

使用上的建议是：

1. 要严格保持现有CASL结果，保留official；常量缓存是已确认等价选项，但不承诺整轮省时。
2. 要提高日常探索效率，可以明确选择FP32/25或BF16/25作为独立工作底座，所有方法在相同底座下重建baseline，保留与官方的对应关系。当前尚未替用户选择。
3. BF三个训练模块可采用已验证负载的graph建议；CASL短训仍保持eager参照。不要把200步短测解释为“整个毕设只需训练200步”。
4. 新创新点只补它自身引入的接口、状态和科学对照，不再次自动扩充一轮泛化准备实验。新数据、预算或临床任务超出现有证据时，在那个具体实验中说明和检查。

明确未覆盖：完整CASL/TBIG/学长论文复现、完整训练收敛等价、LPIPS与临床任务质量、14/28线新确认、OpenH-RF或CT/MRI迁移、Torch优化原型的正式闭环采用。这些边界不是本轮仍欠跑的一串默认任务。
